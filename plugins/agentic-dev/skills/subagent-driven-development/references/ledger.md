## Workspace layout

`scripts/init-workspace.sh <spec-or-plan-file>` creates this inside the repo that holds the
document. `<topic>` is the file name without `.md` and without a trailing `-design` or `-plan`,
so `docs/specs/2026-10-13-x-design.md` and `docs/plans/2026-10-13-x-plan.md` share one
workspace:

```
.delivery/<topic>/              # excluded from git via .git/info/exclude
├── progress.md                 # the ledger, the only file you edit by hand
├── audit-spec.md               # spec audit (Architectural only)
├── preflight.md                # plan pre-flight audit (Architectural only)
├── task-<N>-brief.md           # generated by task-brief.sh; regenerate after new rulings
├── task-<N>-report.md          # written by the implementer
├── task-<N>-review.md          # written by a task-reviewer (large tasks only)
├── gate.md                     # gate audit
└── consult-<topic>.md          # auditor consults
```

In multi-repo work, keep one workspace in the repo that holds the spec and plan. Its ledger
tracks every repo. Run both scripts from the main checkout, never from a temporary worktree,
because the workspace must outlive every worktree.

## Ledger format

The first line names the document the workspace was created from. Then come the header, the
lifecycle checklist and an append-only log. Append lines and never rewrite history. If an entry
was wrong, add a correcting line.

```
# Ledger: docs/specs/2026-10-13-session-resume-design.md
Plan: docs/plans/2026-10-13-session-resume-plan.md
Class: architectural   Branch: feat/session-resume
Repos: ~/src/server @ 1a2b3c4, ~/src/client @ 5d6e7f8
Budget: 25 dispatches / 3 audits   Used: 9 / 3
Models: auditor=<value>  strong=<value>  standard=<value>  fast=<value>

## Lifecycle
- [x] 1. Explore and brainstorm; class stated to the owner; model roles resolved
- [x] 2. Spec written and committed (Bounded: short spec inline at the top of the plan)
...

## Log
Audit spec: APPROVE WITH CHANGES (0 Critical, 2 Important, 3 Minor) -> audit-spec.md
Owner: approved spec (2026-10-13)
Audit preflight: EXECUTE AFTER FIXES (1 Critical, 2 Important) -> preflight.md
Ruling R1 (Task 2) [preflight F1]: store resume tokens hashed, not raw. Why: a DB leak would allow replay. Cost if wrong: one extra hash per resume.
Ruling R2 (global) [preflight F3]: all new errors wrap the existing SessionError type. Why: keeps the error surface stable. Cost if wrong: a later refactor of the error enum.
Ruling R3 (Task 2, Task 4) [controller]: the token TTL is 15 minutes. Why: the spec says "short". Cost if wrong: a config change.
Owner: plan reviewed, OK to execute (2026-10-13)
Task 1: dispatched (mechanical implementer, fast model, BASE 1a2b3c4)
Task 1: reviewed by controller (clean)
Task 1: complete (9f8e7d6, review clean)
Task 2: dispatched (implementer, standard model, BASE 9f8e7d6)
Task 2: reviewed by controller (2 Important -> fix round 1)
Task 2: fix round 1 sent (same implementer)
Task 2: complete (4c5d6e7, review clean after 1 fix round)
Gate: full suite green (server 412 passed 0 skipped; client 88 passed)
Audit gate: MERGE AFTER FIXES (0 Critical, 1 Important) -> gate.md
Gate fixes: dispatched (hard fixer, strong model, BASE 4c5d6e7)
Gate fixes: complete (7a8b9c0, re-reviewed clean)
Pending owner: OK to push and tag v1.4.0? (blocks the release)
Owner: OK to merge and tag v1.4.0 (2026-10-14)
Merged: server main @ 0d1e2f3, tag v1.4.0
```

Keep each entry on one physical line. `task-brief.sh` greps the `Ruling` lines, and you will grep
the rest during recovery. Add a `Plan:` header line once the plan exists, fill in `Models:` as
[models.md](models.md) describes, and update `Used:` whenever you dispatch.

## Writing rulings

`Ruling R<n> (<scope>) [<source>]: <decision>. Why: <reason>. Cost if wrong: <consequence>.`

- **scope** is `Task N` for one task, a comma list such as `Task 2, Task 5` for several, or
  `global` for every task. `task-brief.sh` copies matching rulings into each brief. It does not
  understand ranges like `Tasks 1-3`, so list the tasks.
- **source** is the finding it answers (`preflight F3`, `gate F1`, `spec F2`) or `controller`
  for ambiguities you resolved yourself.
- **Cost if wrong** makes you price the decision. If the cost is high and you are unsure, ask
  the owner or consult the auditor before ruling.
- After adding rulings, regenerate the briefs of tasks that have not started yet. If the task is
  already running, send the ruling text to its implementer with SendMessage.

## Recovery after compaction or restart

1. Find the workspace: `ls .delivery/` in the repo, or search for `progress.md` files.
2. Read `progress.md` in full. The header names the spec, the plan and the resolved models, and
   the lifecycle shows the phase. Keep dispatching with the models on the `Models:` line. If
   it still shows `<value>` placeholders, resolve the roles again with [models.md](models.md)
   before any dispatch.
3. Check each repo's `git log --oneline <base>..HEAD` against the ledger:
   - a commit with no `complete` line means the task finished but was never reviewed, so
     review it now;
   - a `dispatched` line with no commits and no report means the task probably died, so check
     `git status` for partial edits before you re-dispatch;
   - a report file with no `reviewed` line means you have a review to do;
   - a `Pending owner` line with no matching `Owner` line is still open.
4. Re-read the plan's Global Constraints and the rulings for the next task before you dispatch.
5. Tell the owner in one line where you are resuming from.

Trust the ledger and `git log` over anything you think you remember.

## After delivery

`.delivery/` is untracked, so a fresh clone won't have it. If the repo keeps delivery records,
copy `progress.md` and `gate.md` next to the plan in the release commit. Otherwise leave them
where they are.
